# 接收端 v0.7.0：实体麦自动兜底与品牌图标（2026-10-31）

## 需求原话

> 如果虚拟的没声音是否能够自动降级到不虚拟的其他麦克风输入设备？

选型结论（用户拍板）：**接收端内部兜底**（不换系统默认设备、上层软件无感知）+
**默认开启、托盘黄灯可见**。

## 机制

| 环节 | 实现 |
|---|---|
| 触发 | 2 秒监测窗内 `pkts` 零增长累计 ≥ `--fallback-after`（默认 10s）→ 启动兜底 |
| 选麦 | `fb_candidates()` 排除一切名字含 CABLE 的输入设备（防自环回灌），WASAPI 优先、非摄像头优先；再对前 4 个候选 `fb_probe()` 各开 0.4 秒量 RMS，**有信号的优先**（空麦口 RMS=0 会被跳过） |
| 采样 | 按设备原生采样率（多为 48k）打开，回调内线性重采样到 16k 进 `buf`，与平板流走同一条播放链 |
| 隔离 | 兜底期间 reader 线程对平板数据**只计数不入缓冲**，两路音频绝不混流 |
| 恢复 | 任一 2 秒窗内 `pkts` 有增长 → `fb_stop()`：关流、清缓冲、托盘回绿 |
| 失败退避 | 全候选打不开 → 60s 后重试；一个候选都没有 → 300s |
| 关闭 | `--no-fallback`；`--record` 诊断模式自动不启用兜底 |

## 为什么必须"探测 RMS"而不是按设备顺序选

本机实测踩出来的：按索引序第一个候选是 **Realtek 麦克风——一个没插东西的空麦口**，
兜底"成功启动"但 CABLE 录到的是死寂（peak=3~8），黄灯骗人。
真正能听见房间声的是摄像头麦（RMS=48）。所以选麦必须以**实测信号**为准，
探测结果逐条写日志（AI 可读：`兜底候选 #20 ... 实测RMS=0`）。

## 验证记录（假客户端灌 800Hz 正弦模拟平板，全程不动真机）

| 状态转换 | 证据 |
|---|---|
| 断流 10s → 兜底 | 13:41:34、13:42:24 两次触发，选中 #19 摄像头麦 @48k→16k |
| 兜底中黄灯 | 托盘像素扫描 amber=18 / green=0 |
| 兜底期间 CABLE 有声 | peak=80 rms=10（安静房间的真实底噪） |
| 数据恢复 → 切回 | 13:42:02、13:42:54 两次，延迟 ≤2s；CABLE 正弦 peak=9005、800Hz/全带能量比 49.2 |
| 恢复后绿灯 | amber=0 / green=19 |
| 端到端回归 | 0.7.0 装机后真平板 WiFi 自动回连，32.9KB/s 推流正常 |

## 品牌图标

`gen_icon.py`（Pillow 程序化绘制，改设计只改这个文件重跑）产出 16~256px 的
`mic-bridge.ico`：深蓝灰圆角底、青绿麦克风+淡蓝声波、右下角琥珀「zc」圆徽
（≤32px 时字放不下，只留琥珀点）。EXE `icon=`、安装包 `SetupIconFile=`、
快捷方式 `IconFilename=` 三处统一。**快捷方式必须指向独立 .ico**：
指向"EXE,0"时 Windows 图标缓存会顽固地留着旧的 PyInstaller 蛇形图标，
`ie4uinit -show` 都冲不掉，换路径才立竿见影。
